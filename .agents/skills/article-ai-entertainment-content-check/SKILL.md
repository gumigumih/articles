# AIとわたしの深夜エンタメ会議 コンテンツ壁打ちチェック

「AIとわたしの深夜エンタメ会議」の記事や企画を、編集・マーケター・AIエンタメ業界インサイダーの3視点、計8ロールで独立にレビューし、読みやすさ、月額980円を払い続ける価値、AI×エンタメの実態との整合性を辛口に検証する。最後に実行可能な改善案を出す。

## 使うタイミング

- 同マガジンの記事下書きについて、読みやすさ、構成、販売価値、違和感、AIエンタメ業界との整合性を確認するとき
- Claude Code CLIが文章化した記事を、公開前にCodexでレビューするとき
- 同マガジンの価格・形式・連載方針を大きく変えるとき
- 同マガジンのタイトル、企画、コンセプトを壁打ちするとき

## 事前確認

対象と関連するルールドキュメントを先に読む。articlesリポジトリでは、少なくとも対象に関係する`AGENTS/common/style.md`、`AGENTS/common/structure.md`、`AGENTS/magazines/ai-entertainment/monetization.md`、`AGENTS/magazines/ai-entertainment/weekly-template.md`を確認し、想定読者、価格、トーン、差別化方針を把握する。既存ルールと矛盾する指摘はしない。

## 8ロール

レビューするロールを選ぶ際に [8ロールの観点](references/review-roles.md) を読む。広い依頼は全8ロール、特定の依頼は該当ロールを適用する。

## 手順

1. 対象と関連ルールを読む。
2. 依頼に応じて視点を選ぶ。「チェックして」「壁打ちして」のように広い依頼や新規立ち上げでは全8ロール、特定の依頼では該当ロールだけを実行する。記事以外では、編集視点を外し、マーケター・インサイダー視点をお題に合わせて調整する。
3. 依存関係のないA・B・C・D・E・Gは、利用可能なら並列に実行する。FはC/D/Eの後、HはGの後に実行する。
4. 結果を統合し、複数ロールで共通する論点を優先する。記事レビューは「該当箇所（引用）→問題・理由→裏付け→修正案」の順にまとめる。
5. 「このままで良い点」と「変えたほうが良い点」の両方を示す。多すぎる場合は重要な上位5件程度に絞る。
6. 改善案を実際に反映するのは、ユーザーが明示的に依頼した場合だけにする。反映時は記事と関連ルールの両方を確認し、片方だけの修正にならないようにする。

## 一般読者パス（記事執筆時・本文修正時は必須）

専門知識のない読者が、冒頭から最後まで一度読んだつもりで確認する。記事の主張や情報量を増やす工程ではなく、読者が途中で立ち止まる箇所を見つけ、意味を保ったまま局所的に直す工程とする。

- 初出のサービス名・モデル名・専門語だけで、何の道具か、何をするものかが分かるか確認する。スプライトシート、GLB、フレーム、モーショントラッキングなど、一般読者が知らない語は短い説明を添えるか、平易な言い方に置き換える。
- 「画像の出口」「実物性」「決定的ではない」のように、意味は推測できても日本語として硬い表現を拾う。抽象的な名詞句や直訳調を、読者が場面を思い浮かべられる述べ方へ直す。
- 公式発表、投稿者による試行、筆者の感想・判断を混ぜない。投稿を製品仕様・再現性・性能・商用導入の根拠に見せる言い回しは避ける。
- 一文が長すぎないか、同じ説明や結論を無料部と有料部で繰り返していないか、見出しと本文の内容がずれていないかを確認する。
- 注意書きが免責文のように浮いていないか確認する。必要な線引きは残しつつ、読者に「何をどう読む記事か」が伝わる文へ置き換える。
- 強い形容詞や煽りが論点より先に立っていないか確認する。画像を埋め込まない、リンク先を案内するなどの判断は、理由が自然に伝わる一文にする。
- 各 finding は「行番号・読者が止まる理由・修正案」で記録し、事実、数値、固有名詞、URL、引用、条件、責任主体を変えない。修正は必要な箇所だけに留め、筆者の会話的な声は残す。

編集後は、冒頭の導入、無料部から有料部への接続、各見出しの直後、最後のまとめを重点的に通読する。自動 lint が依存関係や環境制限で実行できない場合は、上記の観点を手動で確認し、未実行であることを報告する。

## 本文修正の委譲

本文変更の明示依頼がある場合だけ、実行前に [Claude修正手順](references/claude-revision.md) を読む。レビューのみでは記事を編集せずCLIも実行しない。修正許可は投稿・画像生成・コミット・pushの許可を含まない。

## 出力上の注意

- 粗探しにせず、良い点も短く示す。ただし主眼は具体的に直せる問題の発見とする
- プロジェクト固有の文体・トーンを一般論で矯正しない
- 機能追加や運用工数の増加を安易に提案しない。有料価値と半自動運用への影響を確認する
- 裏付けのない実例を作らず、検索で確認できなかった事実は「未確認」と明示する
- 外部検索・サイト閲覧などはレビューに必要な範囲に限定し、note・Xへの投稿や公開は行わない。対象が同マガジン以外の記事なら、このスキルを使わず、汎用的なレビューとして扱う
