# AIとわたしの深夜エンタメ会議：記事候補調査

## 目的

「AIとわたしの深夜エンタメ会議」の次回記事候補を、読者が記事後に判断できる材料になるかという基準で調査・比較し、チャットで推薦する。通常回は、**第1部「AI分野最新情報」**と**第2部「テーマ特集」**の二部構成を前提に、ニュース候補とテーマ候補を分けて保存する。候補メモを保存するが、この記事本文、カバー画像、X投稿、PPTXはこのスキルでは作成しない。

## 使うタイミング

- ユーザーが「今週の記事候補を調べて」「候補を出して」と依頼したとき
- 月・木曜の定期調査タスクで、次回記事の候補を更新するとき
- PR TIMESを含むAI×エンタメのニュースを、記事化できる厚みまで比較するとき

候補がすでに選択されている場合や、本文・付属スライドを作る依頼は`ai-entertainment-article-package`へ渡す。

通常回では、ニュース候補だけでなく、複数事例を束ねて判断軸を作れるテーマ候補を最低1件提示する。テーマ候補は単なるニュースの再要約ではなく、比較対象、中心仮説、読者が持ち帰る判断基準、スライド化できる構造を含める。

## 事前確認

最初に、`AGENTS/README.md`、`AGENTS/platforms/note/README.md`、`AGENTS/common/writing-workflow.md`、`AGENTS/magazines/ai-entertainment/article.md`を読む。通常回は`AGENTS/magazines/ai-entertainment/weekly-template.md`と`AGENTS/magazines/ai-entertainment/monetization.md`も読む。直近記事と既存の`topics/*-candidates.md`を確認し、重複を避ける。

## 調査と評価

1. 調査期間を明記し、公式ニュースルーム、主要サービス、PR TIMES、独立報道、Xの利用報告・反応を調べる。
2. AI基盤・LLM、個人創作、AIエンタメサービス、権利・流通・ファン体験を横断する。薄い分類を無理に埋めない。
3. PR TIMESは企業・サービス提供者の発表として扱う。公式情報、独立報道、利用報告を分け、発表だけで導入効果や市場性を断定しない。
4. 候補ごとに、発表日、発表元、概要、中心仮説、読者が得る判断材料、価格・提供形態、制作・運用の変化、話題性、独立確認、未確認事項、記事化を見送る条件、直近号との重複を整理する。
5. 記事化推薦は、スライド化しやすさではなく、読者への有用性、分析の厚み、根拠、鮮度、マガジンとの相性を優先する。スライド化適性は補助評価として別欄に記録する。
6. 採用候補ごとに、Xの利用報告または反応を1〜3件確認する。公式デモ、スポンサー投稿、個人の試行、単なる賛否を区別し、本文の仕様・導入実績の根拠には使わない。直接確認できない投稿は未確認として残し、断定しない。
7. 通常回のテーマ候補は、採用候補ニュースから作る場合でも、追加の比較事例・反例・権利やUXなどの評価軸を確認し、ニュース部と同じ内容の繰り返しにならないようにする。

## ソースごとの調査対象数

調査開始時に、ソースごとの目標件数と実績件数を置く。件数は記事化候補のノルマではなく、公式発表だけ・PR TIMESだけに偏っていないかを確認するための目安である。同じニュースが複数ソースに出た場合は、**延べ件数**と**重複除去後のユニーク候補数**を分けて記録する。

| ソース | 入口で見る件数の目安 | 役割 |
| --- | ---: | --- |
| 公式ニュースルーム・公式サービスページ | 4〜6件 | 発表内容、提供状況、価格、仕様の一次確認 |
| 独立報道・業界メディア | 3〜5件 | 話題の広がり、第三者の論点、業界文脈 |
| PR TIMES・企業リリース | 2〜4件 | 国内サービス・イベント・企業発表の発見。効果の根拠とは分ける |
| X | 推薦候補ごとに1〜3件 | 利用報告・反応・公式デモの確認。採用候補以外は必要に応じて確認 |
| Reddit・Hacker News等のコミュニティ | 重要候補ごとに1〜3件 | 実利用の困りごと、品質反応、反対意見の補助確認 |

通常は公式・独立報道・PR TIMESから延べ9〜15件を入口として拾い、重複除去後に候補7〜10件へ整理する。特定ソースで件数が目標未満になった場合は、無理に埋めず「未取得」「対象期間に該当なし」「アクセス不能」を記録する。Xとコミュニティは候補の仕様を増やすためではなく、話題性や利用実態を確認するために使う。

保存メモには、次のようなソース別集計を置く。

```text
公式: 5件（ユニーク候補4件）
独立報道: 4件（ユニーク候補3件）
PR TIMES: 3件（ユニーク候補2件）
X: 12投稿（推薦4候補に各1〜3件、未確認2候補を含む）
コミュニティ: 6投稿（重要候補4件を確認）
```

この集計は調査の透明性のためのもので、点数へ機械的に加点しない。独立報道や利用報告が少ない候補は、根拠の強さ・話題性の点数を下げ、企業発表だけで成立するかを別途判断する。

## 候補の評価軸と絞り込み

候補を並べただけで推薦しない。まず7〜10件程度を広めに調査し、同じ基準で仮スコアを付けてから、記事化推薦3〜6件へ絞る。点数は客観的な真理ではなく、候補同士の比較と「なぜ残したか」を説明するための道具として使う。

### 必須の足切り条件

- 公式発表、公式サービスページ、当事者の発言など、最低1本の一次情報があること。一次情報が見つからない話題は「確認不能」に分ける。
- 発表内容と、実装済み・提供中・実証中・構想段階を区別できること。区別できない候補は推薦に入れない。
- AI×エンタメとして、制作、視聴、ゲーム、音楽、ファン体験、権利・流通のいずれかの具体的な変化を説明できること。単なるモデル発表や企業ニュースは補欠・見送りにする。
- 記事化する場合に、未確認事項と見送る条件を明記できること。企業発表だけで効果・市場性・安全性を断定する必要がある候補は推薦に入れない。

### 仮スコア（各0〜5点、合計35点）

| 評価軸 | 0点 | 5点 |
| --- | --- | --- |
| 読者の判断価値 | 読者の行動・選択に関係しない | 価格、使いどころ、導入条件、権利などを具体的に判断できる |
| 分析の厚み | 要約で終わる | 事業性・UX・技術・権利・運用の複数視点を根拠付きで掘れる |
| 根拠の強さ | 出所不明・転載中心 | 一次情報、独立報道、利用報告が役割ごとに揃う |
| 鮮度・話題性 | 時期不明・反応なし | 調査期間内の発表で、複数媒体やSNSで同時期に議論がある |
| マガジン適合 | AI×エンタメとの接点が薄い | ぐみの実装リード視点と読者層に自然につながる |
| 具体性・検証可能性 | 価格・提供形態・デモ・導入条件が不明 | 実際に試す/比較する/導入判断する材料が複数ある |
| 直近号との差別化 | 主張・企業・カテゴリがほぼ同じ | 新しい切り口やカテゴリ分散を作れる |

目安として、**25点以上を推薦候補、20〜24点を補欠、19点以下を見送り**とする。ただし、必須の足切り条件を満たさない候補は点数にかかわらず推薦しない。Xの投稿が未確認でも、一次情報と独立報道で十分に成立する場合は根拠の強さを下げたうえで残してよい。一方、Xの利用報告が切り口の中心になる候補は、個別投稿を確認できなければ推薦から外すか、公式情報だけで成立する切り口へ変更する。

### 絞り込みの手順

1. 候補7〜10件を、発表日・分類・一次情報・独立確認・X確認状況つきで一覧化する。
2. 全候補へ7軸の仮スコアと短い採点理由を付ける。点数だけでなく、特に高かった軸と低かった軸を残す。
3. 足切り条件に触れる候補を「確認不能」「補欠」「見送り」へ分離する。
4. 25点以上から、直近号との重複、カテゴリ分散、候補同士の論点重複を調整して3〜6件を推薦する。点数順をそのまま掲載順にしない。
5. 推薦候補には「なぜ残したか」「何が未確認なら落とすか」を一文で付ける。補欠から繰り上げる条件も必要なら明記する。
6. チャットでは、推薦候補のスコア概要、最有力候補、補欠・見送り理由、掲載順2〜3案を提示する。

## 保存するメモ

`topics/YYYYMMDD-candidates.md`へ、ソース別の目標件数・実績件数、候補7〜10件程度、評価軸・仮スコア一覧、記事化推薦3〜6件、重要発表の見送り一覧、X確認状況、2〜3通りの掲載順を保存する。通常回は、**第1部の最新情報候補**と**第2部のテーマ候補**を別見出しにする。テーマ候補には、比較事例、中心仮説、評価軸、スライドの役割案を含める。記事化推薦の節と、記事候補とは別の補助事例・スライド化メモの節も分ける。

記事化推薦の各項目には、少なくとも次を含める。

- 記事で問う中心仮説
- 読者が得る判断材料
- 一次情報・独立報道・利用報告の区分
- 未確認事項と記事化を見送る条件
- 事例スライド化適性（高・中・低）を記事化順位と分けて記録
- 7軸の仮スコア合計と、採点理由または特に高低だった軸
- 通常回テーマ候補の場合は、比較事例、中心仮説、テーマ用の評価軸、スライド化適性と6枚程度の役割案

## チャットでの出力

メモを保存するだけで完了にしない。チャットで以下を提示する。

- 記事化推薦3〜6件と、各候補の一文の切り口
- 通常回の第1部（最新情報）候補と、第2部（テーマ特集）候補を分けた構成案
- 最有力候補と、その理由
- 根拠が弱い候補・未確認事項
- 掲載順の選択肢2〜3通り（各案の最初の候補と向く目的を含む）

この出力は候補・構成の提案であり、本文作成、画像生成、PPTX生成、note/Xへの投稿、コミット、pushの許可ではない。ユーザーが候補と掲載順を選択した後、`ai-entertainment-article-package`へ承認内容と調査メモを渡す。
